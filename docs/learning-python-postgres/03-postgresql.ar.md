# 03 · PostgreSQL: أين تعيش البيانات؟

[الفهرس](README.ar.md) · [التالي: الباك إند](04-backend.ar.md)

الواجهة تعرض قيمًا مؤقتة في الذاكرة. PostgreSQL تحفظ البيانات التي نريد استرجاعها لاحقًا. الخادم وحده يتصل بها عبر psycopg. إنشاء كائن Preferences في Python لا يحفظه؛ INSERT أو UPDATE داخل معاملة ناجحة هو ما يفعل ذلك.

## من الخادم إلى الصف

الخادم PostgreSQL برنامج مستقل. داخله database باسم hatim في إعداد التطوير، وداخلها schema عادة public، وداخل schema جداول. schema بهذا المعنى مساحة أسماء؛ وقد تستعمل الكلمة أيضًا لوصف تصميم البيانات عمومًا. كل جدول يحتوي صفوفًا، وكل صف له أعمدة وأنواع وقيود.

## كل عمود في المخطط الحالي

المصدر: [ملف SQL كاملًا مع الشرح](code/backend-migrations-001_groups_and_members.sql.ar.md).

| الجدول والعمود | النوع | لماذا يوجد؟ |
|---|---|---|
| groups.id | TEXT PRIMARY KEY | معرف ثابت للمجموعة، ليس اسمها المعروض |
| groups.title | TEXT NOT NULL | اسم المجموعة؛ الافتراضي يأتي من CreateGroup |
| groups.invite_code | TEXT UNIQUE NOT NULL | رمز رابط الدعوة؛ مستقل عن مفتاح الإدارة |
| groups.owner_hash | TEXT UNIQUE NOT NULL | بصمة مفتاح المنظّم الذي يتحقق منه الخادم |
| groups.settings | JSONB NOT NULL | slots وanchor_id وpocket_ids وcompleted_ids |
| groups.created_at | TIMESTAMPTZ | وقت الإنشاء؛ القيمة الافتراضية CURRENT_TIMESTAMP |
| members.id | TEXT PRIMARY KEY | معرف العضوية في هذه المجموعة |
| members.group_id | TEXT REFERENCES groups | المجموعة المالكة للعضو؛ علاقة واحد إلى متعدد |
| members.token_hash | TEXT UNIQUE NOT NULL | بصمة مفتاح تعديل ملف العضو |
| members.preferences | JSONB NOT NULL | الاسم والمطابخ والحساسية والميزانية وغيرها |
| members.organizer | BOOLEAN DEFAULT FALSE | هل صف العضو يمثل المنظّم؟ |
| members.created_at | TIMESTAMPTZ | وقت إنشاء العضوية |
| members.sequence | BIGINT GENERATED ALWAYS AS IDENTITY | رقم يولده PostgreSQL لكسر تعادل أوقات الأعضاء |
| schema_migrations.version | TEXT PRIMARY KEY | اسم ملف الترحيل الذي طُبق |
| schema_migrations.checksum | TEXT NOT NULL | بصمة محتوى ذلك الملف |
| schema_migrations.applied_at | TIMESTAMPTZ | متى طبق الترحيل؟ |

`NOT NULL` يمنع القيمة المفقودة، ولا يمنع نصًا فارغًا؛ Pydantic يمنع الاسم الفارغ في المدخلات. `UNIQUE` يمنع تكرار القيمة بين صفوف الجدول. `PRIMARY KEY` يعرّف الصف ويجمع عدم التكرار وعدم NULL. `FOREIGN KEY` يمنع عضوية تشير إلى مجموعة غير موجودة.

`ON DELETE CASCADE` يعني أن حذف صف مجموعة في DB يحذف صفوف أعضائها. وجود هذه القاعدة لا يعني وجود زر أو endpoint لحذف المجموعة؛ هذا غير منفذ في النسخة الحالية. الفهرس `members_group` يساند قراءة الأعضاء حسب المجموعة والوقت والترتيب. الفهرس الجزئي `one_organizer_per_group ... WHERE organizer` يمنع منظّمين اثنين في المجموعة، لكنه وحده لا يضمن وجود منظّم واحد على الأقل. إنشاء المجموعة والعضو المنظّم معًا هو ما يحقق حالة البداية.

عدد 12 لا توجد له CHECK في SQL؛ يفرضه API بقفل صف المجموعة قبل العد. كتابة بيانات مباشرة من خارج API تتجاوز هذه القاعدة، لذلك وصول التطبيق المعتاد يكون عبر الخادم.

## لماذا JSONB؟

مثال إعدادات توضيحي:

```json
{"slots":3,"anchor_id":"fire","pocket_ids":["coffee"],"completed_ids":[]}
```

JSONB نوع داخل PostgreSQL، يمكن الاستعلام عن حقوله. في هذا التصميم الصغير نقرأ الملف الشخصي والإعدادات كاملين غالبًا، فكان تجميعهما مباشرًا. `CHECK (jsonb_typeof(settings) = 'object')` يرفض JSON من نوع قائمة أو رقم، لكنه لا يفحص ميزانية أو معرف تجربة؛ ذلك مسؤولية Pydantic وقواعد API هنا.

المقابل: معرفات التجارب داخل JSONB لا تملك foreign keys إلى جدول تجارب، والكتالوج أصلًا ثابت في Python. إذا جعلتِ التجارب قابلة للتحرير في نسختك، فراجعي فصل علاقاتها إلى جداول وتحديد سلوك حذفها. لا يعني البساطة تجاهل ما لا تضمنه قاعدة البيانات.

## كيف تقرئين SQL؟

```sql
SELECT id, group_id, organizer
FROM members
WHERE group_id = 'practice-group'
ORDER BY created_at, sequence;
```

SELECT يحدد الأعمدة، FROM الجدول، WHERE الصفوف المقبولة، ORDER BY ترتيبها. الاسم هنا مثال تدريبي. في API لا ندمج معرف المستخدم نصيًا، بل نستخدم:

```python
db.execute(
    "SELECT * FROM members WHERE group_id=%s ORDER BY created_at, sequence",
    (group_id,),
)
```

`%s` مكان قيمة يربطها psycopg، وليس تنسيق نص بـ% أو f-string. tuple الثاني يرسل القيم منفصلة. `fetchone()` يأخذ صفًا واحدًا أو None، و`fetchall()` قائمة صفوف. `dict_row` يسمح بقراءة `row["id"]`. أسماء الجداول ليست values؛ اختبار schema يستخدم `sql.Identifier` عند بناء اسم ديناميكي. [استخدام psycopg الرسمي](https://www.psycopg.org/psycopg3/docs/basic/usage.html).

INSERT ينشئ صفًا. UPDATE يغيّر أعمدة الصفوف المطابقة لـWHERE. DELETE يحذف المطابق. حذف WHERE من UPDATE/DELETE قد يؤثر على كل الجدول؛ تدربي في DB منفصلة، ولا تستخدمي قاعدة بيانات المجموعات الحالية للتجارب التعليمية.

## المعاملة: كل العملية أو لا شيء

إنشاء المجموعة يحتاج صفًا في groups وصفًا في members. لو حفظنا الأول ثم فشل الثاني، سنترك مجموعة ناقصة. لذلك يعملان داخل `with connect() as db` واحدة. عند الخروج الطبيعي يثبت psycopg التعديلات بـcommit، وعند خروج استثناء يتراجع بـrollback، ويغلق الاتصال. حتى لو ظهر return داخل with، يجري الخروج من السياق قبل تسليم النتيجة النهائية. [سلوك سياق الاتصال](https://www.psycopg.org/psycopg3/docs/basic/usage.html).

القراءات تستخدم REPEATABLE READ READ ONLY: قراءة المجموعة ثم أعضائها تشاهدان لقطة متسقة داخل نفس المعاملة. التعديلات تستخدم مستوى PostgreSQL الافتراضي READ COMMITTED مع `FOR UPDATE` على المجموعة. إذا كان عدد الأعضاء 11 وحاول اثنان الانضمام، الأول يقفل ويقرأ 11 ويضيف العضو 12. الثاني ينتظر، ثم يقرأ العدد الملتزم الجديد 12 ويرفض بـ409.

هذا لا يدمج تلقائيًا تحرير إعدادات من جهازين. PUT يرسل نسخة إعدادات كاملة؛ آخر طلب ناجح قد يستبدل اختيارات جهاز آخر القديمة. قفل DB يحمي سلامة العملية، وليس تاريخ نوايا المستخدم. تطبيق يتوسع للتحرير المتزامن قد يحتاج version أو شروط تحديث؛ لا ندّعي أنها موجودة هنا.

## store.py من البداية للنهاية

`database_url` يقرأ DATABASE_URL من بيئة الخادم ويرفض غيابها، فلا يوجد fallback إلى SQLite. `connect` ينشئ اتصالًا لكل عملية، يضبط مهلة اتصال 5 ثوانٍ ومهلتي statement وlock بعشر ثوانٍ، ثم يسلمه بـyield. لا يوجد ORM أو pool صريح في هذا الكود.

`initialize` يجد migrations بالنسبة إلى مسار الملف، لا إلى المجلد الذي صادف أن شغّلتِ الأمر منه. يأخذ advisory lock حتى لا ينشئ عاملان المخطط بالتزامن. ينشئ جدول تاريخ الترحيلات إن لم يوجد، ويقرأ ملفات SQL بالترتيب، ثم يحسب بصمة كل ملف. الملف المطبق يُتجاوز إذا طابقت بصمته، ويرفض التشغيل إن تغير. الملف الجديد ينفذ ويسجل في نفس المعاملة.

الأرقام مهمة: استعملي أسماء مثل 001 و002 كي يكون ترتيب النصوص هو الترتيب المقصود. لا تعدّلي 001 بعد تطبيقه؛ أضيفي migration جديدة. هذا التحقق ليس نظام down migrations أو أداة استعادة تلقائية.

## لماذا بقي import_sqlite.py؟

هو أداة نقل للبيانات السابقة فقط. يفتح المصدر read-only، ويأخذ backup متسقة تشمل البيانات الملتزم بها في WAL. يرتب الأعضاء بوقت الإنشاء وrowid القديم، ثم ينسخ إلى PostgreSQL فارغة داخل معاملة واحدة، مع الاحتفاظ بالمعرفات ورموز الدعوة والبصمات والتفضيلات والأزمنة. sequence الجديدة تحافظ على ترتيب التعادل.

قبل commit يقارن السجلات المستوردة بالمصدر بعد تحويل الأنواع. اختلاف أو مصدر غير صالح يفشل العملية ويرجع التعديلات. وجود صفوف مسبقًا في الوجهة يوقف النقل بدل دمج أو حذف البيانات. `timestamp` يعامل وقت SQLite القديم الخالي من timezone كUTC. النسخة الأصلية والbackup تبقيان محليتين؛ الخادم الجاري يستعمل PostgreSQL فقط.

عند بناء مشروع جديد لا تحتاجين SQLite ولا أداة النقل أصلًا. تعلميها لاحقًا لفهم الترحيل الآمن، ولا تشغليها للتدرب على قاعدة مستخدمة.
