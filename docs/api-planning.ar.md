# عقد API — الخطة المباشرة ورفقة الطلعة

التنفيذ الآن في `backend/hatim/features/planning/router.py` و`service.py`، والعميل في `src/features/planning/api.ts`. إعادة الهيكلة في16سبتمبر2026 تحفظ العقد والمسارات التالية دون تغيير؛ [دليل التوسعة](architecture-modules.ar.md).

هذا أساس التخطيط المتاح دون حساب أو قروب دائم. كلمة `groups` في الجداول والمسارات موروثة من أول نسخة، وتعني الخطة الواحدة ورفقتها. القروب الدائم مختلف وله [API تحت /api/v2](api-social.ar.md). كلاهما يستخدم محرك القرار نفسه.

## إنشاء خطة

`POST /api/groups` يقبل preferences وtitle اختياريًا وsettings اختياريًا. دون Authorization يرجع201 و`{organizer_token, group}` لخطة ضيف. مع جلسة حساب صالحة تُربط الخطة بالمالك وتكون organizer_token=null؛ يستخدم العميل جلسة الحساب لإدارتها. الجلسة المرسلة غير الصالحة تعيد401، ولا تتحول إلى إنشاء ضيف. لا ترسل مفاتيح الإدارة إلى المدعوين.

```json
{
  "preferences": {"name": "أمل", "budget": 200, "allergies": []},
  "settings": {"slots": 3, "anchor_id": "sushi", "pocket_ids": [], "completed_ids": []}
}
```

للبدء دون ركيزة أرسل `anchor_id: null`. لحفظ تجربة أولًا في الجيب، أرسل معرفها داخل pocket_ids مع ركيزة null. الواجهة الجديدة ترسل Settings صراحة. إذا أغفلها عميل قديم تبقى القيم السابقة:٩ خانات وركيزة fire. لا تتغير خطة موجودة بسبب هذا التعديل.

Pydantic يفحص الأسماء والحدود وقواعد Settings: الخانات١–٩، وعدم تكرار المعرفات أو وضع الركيزة أو تجربة مكتملة في الجيب. `validate_settings` يفحص وجود المعرفات في الكتالوج عند الإنشاء والتعديل. الفشل422 ولا تنشأ خطة جزئية. الإعدادات والتفضيلات تحفظ في معاملة PostgreSQL واحدة؛ اختيار الركيزة لا يحتاج طلب كتابة ثانٍ.

## المسارات

| الطريقة والمسار | المستخدم | النتيجة |
|---|---|---|
| GET /api/experiences | الجميع قبل الإنشاء | التجارب التوضيحية من PostgreSQL؛ نفس كتالوج v2 |
| POST /api/groups | ضيف أو حساب صالح | خطة ومفتاح ضيف، أو خطة محفوظة للحساب |
| GET /api/groups | جلسة الحساب | PlanSummary[] لخططه فقط: id، title، slots، consumed |
| PUT /api/groups/{id}/account | جلسة الحساب وowner_token في الجسم | حفظ خطة الضيف في الحساب دون إنشاء circle |
| PUT /api/groups/{id}/title | المالك | title من1 إلى60 حرفًا، ثم GroupView |
| DELETE /api/groups/{id} | المالك | حذف الخطة ورفقتها وإلغاء دعوتها، ثم {ok:true} |
| GET /api/groups/{id} | مفتاح المنظم | الإعدادات والأعضاء والتفضيلات والخطة وأسبابها |
| PUT /api/groups/{id}/settings | مفتاح المنظم | حفظ الخانات والركيزة والجيب والمكتمل وإعادة الحساب |
| PUT /api/groups/{id}/profile | مفتاح المنظم | تعديل ذوقه وإعادة الحساب |
| DELETE /api/groups/{id}/members/{member} | مفتاح المنظم | إزالة رفيق من الخطة وإلغاء مفتاحه مع حماية المنظم |
| GET /api/invites/{code} | رابط الدعوة | عرض محدود للخطة وأسماء الرفقة دون تفضيلاتهم |
| POST /api/invites/{code}/members | المدعو دون حساب | preferences في الجسم، ثم member وmember_token |
| GET /api/invites/{code}/me | مفتاح المدعو | بياناته وحده |
| PUT /api/invites/{code}/me | مفتاح المدعو | تحديث تفضيلاته |

المفاتيح تمر في `Authorization: Bearer ...`، والرابط يحمل رمز الدعوة فقط. «مفتاح المنظم» في الجدول يعني capability للضيف أو جلسة صالحة للحساب المالك عندما تكون الخطة مرتبطة. GroupView يتضمن owner_account_id=null للضيف أو معرف مالك الحساب؛ InviteView لا يعرض هذا المعرف. 404 يعني موردًا أو مفتاحًا غير متاح، و409 يمنع تعديل خطة نُقلت صراحة إلى قروب دائم أو مسح إعدادات أحدث.

## الحفظ للحساب والتزامن

PUT /api/groups/{id}/account يقبل `{owner_token: "..."}` ويتحقق من مفتاح خطة الضيف مع قفل صفها. يضيف owner_account_id ويستبدل بصمة المفتاح القديم، دون نسخ خطة أو تغيير رمز الدعوة والأعضاء والذوق والجيب. الحساب نفسه يستطيع تكرار الطلب بعد فقد الرد، والحساب الآخر يُرفض404. الربط لا يسمح بتحويل خطة سبق نقلها إلى circle؛ يرفضها409. خطة مرتبطة بحساب لا تقبل مفتاح الضيف السابق ولا يمكن نقلها عبر legacy/claim القديم.

تعديل Settings يقبل حقولها السابقة مع expected اختياري يحوي آخر Settings قرأها العميل. ترسل الواجهة الحالية `{...settings, expected}`. يقارن الخادم expected بالحالة الموجودة تحت القفل، ويرجع409 إن تغيّرت. لا تُخزن expected في DB. العملاء السابقون الذين لا يرسلونها يحتفظون بالتوافق دون حماية المقارنة؛ تحديث التطبيق مطلوب للاستفادة منها. ظهور409 يستدعي تحديث الخطة ومراجعة الاختيار، وليس إعادة كتابة تلقائية.

تسجيل الخروج يلغي الجلسة الحالية؛ لا يعمل مفتاحها لقراءة أو تعديل خطة الحساب. جلسات الأجهزة الأخرى تبقى صالحة. حذف الخطة نهائي بعد تأكيد الواجهة، ولا يحذف الحساب أو بقية الخطط أو القروبات. المدعو لا يستطيع الحذف بمفتاحه.

## تحويل اختياري إلى قروب دائم

فتح «قروباتي» وحده لا ينقل الخطة أو الرفقة. بعد الدخول يستطيع صاحب مفتاح الخطة استعمال إجراء الربط الموجود. ينقل الخادم آخر الإعدادات والتفضيلات إلى قروب وطلعة أولى في معاملة، ثم يزيل العميل مفتاح الخطة السابقة من تخزينه. تصبح إدارة النسخة المنقولة من القروب، ويبدأ المسار المباشر دون خطة عند الرجوع. تحفظ البيانات الأصلية للتوافق ويمنع تعديلها بعد النقل.

تصحيح البداية في الفصل15 لم يحتج ترحيلًا. إضافة الحساب إلى الخطط في الفصل16 تستخدم الترحيل003 لإضافة owner_account_id وفهرسه. المصدر الآلي هو [OpenAPI](../backend/openapi.json)، و[شرح الإضافة الحالية](learning-python-postgres/16-accounts-and-school.ar.md).
