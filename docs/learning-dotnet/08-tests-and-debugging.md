# ٨ — الاختبارات وتصحيح الأخطاء

[الفهرس](README.md) · [التالي: البناء المستقل](09-build-it-yourself.md)

الاختبار كود يثبت سلوكًا محددًا: نجهز مدخلات، ننفذ الفعل، ونقارن بالمطلوب. نجاح build يعني أن المترجم قبل الكود؛ لا يعني أن الركيزة بقيت أو أن عضوًا لا يستطيع تعديل مجموعة أخرى.

## ثلاثة مستويات في حاتم

| المستوى | ما يختبره؟ | لماذا؟ |
|---|---|---|
| PlannerTests | دوال القرار مباشرة | سريع ويعزل القاعدة عن الشبكة والشاشة |
| ApiTests | HTTP حقيقية داخل test host مع DB مؤقتة | التحقق والحفظ والصلاحيات وتركيب الرد |
| Playwright | متصفح يتفاعل مع الواجهة والـAPI | التأكد من اكتمال رحلة المستخدم وربط الأجزاء |

هذه النسخة تحوي ١٨٠ حالة مقارنة محفوظة للمخطّط، واختبارات خصائص وتكامل إضافية. أسماء الاختبارات التي تذكر اللغة القديمة تصف سبب وجود بيانات التوافق، ولا تشغّل خادمًا قديمًا أو تتطلب تعلّم لغته.

## PlannerTests.cs: شرح كل اختبار

[الملف](../../backend/Hatim.Api.Tests/PlannerTests.cs)، ٨٣ سطرًا. using يستورد DataAnnotations وأنواع التطبيق وxUnit. Catalog حقل مشترك للقراءة. ParityCase record يحمل الأعضاء والإعدادات والخطة المتوقعة. `Cases` تقرأ JSON إلى قائمة، وCaseNumbers تعيد أرقامًا من صفر إلى طولها ناقص واحد.

`[Fact]` حالة اختبار واحدة. `[Theory]` نفس الاختبار بعدة مدخلات. MemberData تشير إلى مصدر بيانات باسم داخل الكود. `Assert.Equal` يقارن المتوقع والفعلي؛ Empty/NotEmpty/NotNull/All/True/False/Contains تصف توقعات أخرى. `Person(...)` مساعد يبني عضوًا افتراضيًا اسمه أمل كي لا تتكرر التهيئة.

| الدالة | المدخل والفعل والضمان |
|---|---|
| `MatchesOriginalPythonDecisions`، ١٥–٢٠ | لكل حالة محفوظة تقارن Plan الناتجة من .NET مع الخطة المتوقعة بعد تحويلهما لنفس JSON، فتكتشف اختلاف البيانات والترتيب والرسائل |
| `ShrinkingOnlyTruncatesAndAccountsForEveryExperience`، ٢٤–٣٨ | تبني خطة كاملة ثم تمر على ١–٩ خانات؛ يجب أن تكون المختارة مقدمة الكاملة وتبدأ fire، وأن تظهر كل تجربة مرة واحدة بين المختار والجيب |
| `AllergyRequiresVerificationAndContradictoryDeclarationAlwaysBlocks`، ٤٠–٥١ | تبني تجربة اختبار موثّقة الغياب، ثم تجعل declaration متناقضة؛ يجب أن يمنع التعارض. الكتالوج غير الموثق مع حساسية ينتج صفر مختار ومشكلة ركيزة |
| `SoftHeatPreferenceWithoutWorkaroundReducesAffinityButDoesNotBlock`، ٥٣–٦٢ | تزيل تعديل الحرارة من bao في نسخة اختبار، وتقارن الشخص العادي بغير محب الحار؛ نقص ٢٠ نقطة دون منع وبنص تفضيل مرن |
| `RankingDoesNotDependOnMemberOrder`، ٦٤–٧٢ | يعكس ترتيب عضوين ثم يقارن معرفات المختار؛ ليس ضروريًا تطابق ترتيب الأسماء داخل النص لنجاح هذه الخاصية |
| `ConsumedAndPocketConstraintsAreValidated`، ٧٤–٨٢ | حالات استهلاك أكبر من الوقت وركيزة في الجيب وتكرار وتداخل؛ `Validator.TryValidateObject` يستدعي تحقق Settings ويجب أن يفشل |

البيانات المتوقعة جيدة لمنع تراجع أثناء نقل تنفيذ، لكنها وحدها قد تحفظ خطأ قديمًا أيضًا. لذلك تُضاف اختبارات مستقلة من قواعد المنتج مثل عدم اختفاء الخانات ومنع حساسية غير موثقة. اختباراتك الجديدة يجب أن تبدأ من المتوقع الذي حسبته، لا من نسخ نتيجة الدالة نفسها إلى المتوقع.

## ApiTests.cs: بيئة اختبار مستقلة

[الملف](../../backend/Hatim.Api.Tests/ApiTests.cs)، ٢٥٦ سطرًا. `TestApp : WebApplicationFactory<Program>` يشغّل التطبيق داخل مضيف اختبار. `Guid.NewGuid` يميز مجلدًا مؤقتًا لكل مثيل. DatabasePath ملف تجريبي في ذلك المجلد، وليس backend/data الحقيقي.

`ConfigureWebHost` تنشئ المجلد. إذا طلب الاختبار legacy تُحمّل legacy.sql إلى DB الجديدة. تكتب index.html بسيطة لفحص تقديم الويب، وتضبط HATIM_WEB_ROOT، وتستبدل تسجيل Store في DI بواحدة تعتمد المسار المؤقت. `RemoveAll<Store>` يزيل القديم وAddSingleton يضع البديل.

`Dispose` تنهي المضيف، وتفرغ connection pools ثم تحذف مجلد الاختبار إن ظل موجودًا. `Directory.Exists` يجعل التنظيف يتحمل استدعاءه بعد تنظيف سابق. هذه آلية حذف **مجلد اختبار أنشأه الاختبار**، وليست تعليمات لمسح بياناتك الحقيقية.

ApiTests نفسها تحتفظ بمضيف وHttpClient، وتمنع التحويل التلقائي كي تستطيع رؤية استجابة redirect. Dispose ينظف الاثنين. `Send` يبني HTTP مع Bearer وJSON إن وُجدا. `Read<T>` يتحقق أولًا من نجاح HTTP ثم يقرأ النتيجة بنوعها. `Create` و`Join` مساعدان لإنشاء بيانات جديدة للسيناريو.

| PayloadLimitAppliesToKnownAndUnknownLengths، ١٩٦–٢١٠ | جسم أكبر من الحد مرفوض سواء أعلن طوله أم لا |

`ChunkedContent` نوع صغير للاختبار يمدد HttpContent. `TryComputeLength` يرجع false كي لا يتوفر طول معلوم مسبقًا، وSerializeToStreamAsync يكتب bytes. هذا يختبر مسار فحص حجم لا تغطيه ContentLength وحدها.

`Task.WhenAll` في اختبار الانضمام يشغّل الطلبات كعمل متداخل بدل انتظار كل واحد قبل التالي. نجاح هذا السيناريو يدعم وجود القفل والمعاملة، وليس وعدًا بأن SQLite مناسبة لأي حجم حركة مرور.

## legacy.sql وplanner-parity.json

[legacy.sql](../../backend/Hatim.Api.Tests/legacy.sql) يبدأ معاملة، ينشئ الجدولين، ويضيف مجموعة وعضوين ببيانات ومفاتيح اختبار معروفة، وينشئ الفهرس ثم COMMIT. القيم ليست بيانات مستخدمين حقيقية. فائدته التأكد أن نقل الخادم لا يتطلب مسح المجموعات السابقة.

[planner-parity.json](../../backend/Hatim.Api.Tests/planner-parity.json) مصفوفة من حالات: members ثم settings ثم plan المتوقعة، بنفس حقول Models التي شرحناها. لا تحتاجين تفسير JSON جديد لكل سطر طويل؛ القواعد واحدة والقيم هي حالات اختبار مختلفة. ليس من الجيد توليد ١٨٠ expected من نفس الدالة المعدلة ثم القول إن المقارنة مستقلة.

## playwright.config.ts

[الملف](../../playwright.config.ts) يحدد tests كمجلد، و٦٠ ثانية مهلة الاختبار، وfullyParallel=false، وعنوان HATIM_TEST_URL أو loopback8000. يحتفظ بـtrace عند الفشل وصورة عند الفشل. مشروع chromium يستخدم خصائص Desktop Chrome وعرض 1440×1100، والـreporter قائمة نصية. لا يوجد webServer في الإعداد، ولذلك لا يشغّل API نيابة عنك.

## tests/group-flow.spec.ts: الحالات الثلاث

[الملف](../../tests/group-flow.spec.ts)، ٢٠١ سطرًا. test يعرف الحالة وexpect يتحقق. `page` تبويب المتصفح، و`request` عميل HTTP للاختبار، و`browser` لإنشاء متصفح/سياق عضو مستقل. اختيار العناصر يكون بالاسم والدور أو testID، لا بإحداثيات ثابتة.

**الحالة الأولى:** تنشئ مجموعة اختبار ثم تعترض طلب الدعوة وترجع 503 نصًا عاديًا. تتأكد من ظهور رسالة الخدمة، تزيل الاعتراض، تضغط إعادة المحاولة، وتتأكد من ظهور فعل إضافة الذوق. الغرض أن يتعافى المستخدم من فشل مؤقت دون تغيير رابط الدعوة.

**الثانية، الرحلة الكاملة:**

1. تجمع أخطاء JavaScript في مصفوفة، وتفتح معاينة المنظّم وتملأ الاسم والذوق. تنتظر رد إنشاء المجموعة قبل متابعة المعرف والمفتاح.
2. تقلص الوقت لعشاء، ثم تفحص UI وAPI أن fire الوحيدة والباقي في الجيب.
3. تنشئ browser context منفصلة بعرض هاتف؛ لها storage مستقلة عن المنظّم. تنضم سارة نباتية وتحب الإيطالي، وتنتظر ظهور تعديل نباتي عند المنظّم.
4. تعيد تحميل صفحة العضو وتثبت بقاء مفتاحه وتمكين التعديل.
5. تضيف حساسية مكسرات، وتتأكد من تعليق الركيزة ومن عدم تسرب نص الحساسية إلى الدعوة العامة، ثم تزيلها لعودة الخطة.
6. تضغط «عشناها» وتفحص consumed=1 وavailable=0، ثم تتراجع وتوسع الوقت.
7. تبحث عن تجربة اليابان وتحفظها في الجيب، وتعيد التحميل وتتأكد من بقاء الحفظ.
8. تغيّر عرض النافذة للهاتف وتلتقط صورًا، وتقارن scrollWidth بـinnerWidth لمنع overflow أفقي، وتتأكد أن errors فارغة، ثم تغلق سياق العضو.

**الثالثة:** رابط غير صالح يعرض رسالة مفيدة ولا يعرض تبويبات المنظّم. هذا اختبار UX أيضًا؛ شاشة الدعوة الفاشلة لا تتحول إلى لوحة إدارة.

الصور وtraces في test-results/ وplaywright-report/ نواتج فحص وليست مصدر التطبيق. اختبار المتصفح يختبر React Native Web؛ لا يثبت مظهر Liquid Glass الأصلي في iOS، الذي يحتاج تحققًا على المحاكي/الجهاز.

## كيف تشغّلين الفحوص؟

```sh
npm run check
npm run format:check
npm run format:api:check
```

للمتصفح، شغلي API مع web export **وقاعدة بيانات تدريب منفصلة**؛ E2E تنشئ مجموعات وتضيف أعضاء في الخدمة المستهدفة. لا توجهها إلى خدمة بيانات شخصية وتفترضي أنها قراءة فقط. مثال من جذر المستودع:

```sh
mkdir -p .run
npm run web:build
HATIM_DB="$PWD/.run/learning-tests.sqlite3" dotnet run --project backend/Hatim.Api --no-launch-profile --urls http://127.0.0.1:8002
```

في طرفية ثانية بنفس الجذر:

```sh
npx playwright install chromium
HATIM_TEST_URL=http://127.0.0.1:8002 npm run test:e2e
```

الأولى تبقى تعمل. `.run` متجاهل في Git. هذا مثال متصفح؛ المحاكي الحالي يثبت عنوان API المحلي على8000، فلا تختبري اتصال المحاكي بـ8002 متوقعة أن يختاره وحده. اختبارات C# تنشئ قواعدها المؤقتة تلقائيًا.

## تشخيص «ما يشتغل» بالترتيب

| الملاحظة | افحصي | السبب المحتمل |
|---|---|---|
| build فاشل | أول رسالة مترجم مع ملف وسطر | نوع أو استيراد أو اعتماد غير صحيح |
| health لا يصل محليًا | هل API تعمل وعلى8000؟ | خدمة مطفأة أو منفذ مختلف/مشغول |
| health يصل وHTML لا يصل | هل dist موجودة؟ | لم تبني الويب أو web root خطأ |
| الويب يطلب API على8081 | عنوان request في Network | شغلتِ dev web بلا proxy بدل المسار الموحد الحالي |
| المحاكي يعمل والهاتف لا | EXPO_PUBLIC_API_URL داخل آخر Release | localhost على الهاتف أو رابط نفق انتهى |
| يظهر خطأ اتصال بعد توقف النفق | health المحلي والرابط العام كل على حدة | النفق مؤقت ويحتاج تشغيلًا وعنوانًا محدثًا |
| الدعوة تصل لكن مجموعتي غير موجودة | نفس origin/المتصفح ومفتاحه | تخزين محلي مختلف أو مفقود |
| الخطة فارغة دون خطأ شبكة | anchor_issue وpocket reasons وconsumed | قيد حقيقي أو خانات مستهلكة، وليس انهيارًا |
| واجهة تبدو قديمة بعد تعديل .env | تاريخ الحزمة المثبتة | يلزم إعادة بناء Release |

ابدئي بسؤال قابل للقياس: «هل GET health يرجع200؟» ثم انتقلي للطبقة التالية. لا تمسحي DB أو كل المحاكي لعلاج خطأ عنوان. ضعي breakpoint عند فعل الحفظ في controller، واقرئي قيمًا تدريبية، وتتبعي الرد في Network، ولا تطبعي مفاتيح مستخدمين في تقارير مشتركة.
