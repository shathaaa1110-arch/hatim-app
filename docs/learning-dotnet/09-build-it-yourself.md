# ٩ — كيف تبنين تطبيقًا مثله بنفسك من الصفر؟

[الفهرس](README.md) · [التالي: فهرس الملفات](10-file-index.md)

هذا تسلسل تعلّم وتنفيذ مقترح، لا ادعاء بأنك تستطيعين اكتساب كل البرمجة في أيام قليلة. لا تنقلي المشروع الحالي كله إلى مجلد جديد ثم تعيدي تسميته. ابني ميزة صغيرة تستطيعين شرح كل مدخل وقرار ونتيجة فيها، ثم زيدي النطاق. وثّقي تعلّمك الفعلي ومصادرك وفق سياسة المدرسة.

## ١. ثلاث تجارب على ورقة

اختاري ثلاثة معرفات A وB وC وبيانات وهمية: سعر ومطبخ ونقاط تحريرية وخيار نباتي. اكتبي عضوين بميزانيات وأذواق. اختاري ركيزة، وطبقي القيود ثم النقاط ثم عدد الخانات يدويًا. **دليل إتقان:** تستطيعين تفسير سبب قبول/رفض كل تجربة، والفرق بين الجيب اليدوي وفائض الوقت والمكتمل.

هذه قواعد البدء التي تقررينها قبل الكود: حجم المجموعة، الخانات، من يعدل ماذا، معنى الحساسية غير الموثقة، هل الميزانية قيد، وهل القهوة خانة. لا تتركي هذه القرارات لألوان الشاشة أو لما تسهله المكتبة.

## ٢. أساسيات C# دون API

في مجلد تدريب منفصل اكتبي برنامج console. الأوامر التالية هي إعداد مشروع صغير، وليست حل المخطّط:

```sh
dotnet new console -n MealRulesPractice -f net10.0
cd MealRulesPractice
dotnet run
```

`new` ينشئ قالبًا رسميًا، و`console` نوعه، و`-n` اسمه، و`-f` الإطار. عدّلي البرنامج بنفسك ليمثل تجربة واحدة، ثم قائمة، ثم عضوًا، ثم فحص ميزانية، ثم ترتيب ثلاثة أرقام. بعد ذلك اكتبي دالة تعيد أسباب المنع. لا تضيفي HTTP قبل أن تعملي مثالًا صحيحًا في console.

**دليل إتقان:** تعديل مدخل واحد يعطي النتيجة التي حسبتها مسبقًا. تستطيعين تفسير string/int/bool/list/if/foreach/return وnull. انتقلي بعدها إلى record وLINQ، وقارني حلقاتك الواضحة باختصارات Planner في الفصل الثاني.

## ٣. أساسيات الواجهة قبل ربطها

تعلّمي JavaScript: كائنات ومصفوفات ودوال وmap/filter وPromise وasync/await. ثم TypeScript والأنواع. ثم React: component/props/state/effect. اكتبي بطاقة تجربة ونموذج اسم وزر حفظ محلي. React Native يستعمل View وText وPressable بدل افتراض أن كل HTML يصلح على الهاتف.

أنشئي مشروعًا فارغًا مستقلًا. هذا tag موجود في npm عند إعداد الدليل ويحدد عائلة SDK57، وقد يتغير patch داخلها؛ للمطابقة الحرفية مع النسخة الحالية مرجعها package-lock.json:

```sh
npx create-expo-app@latest MyMealApp --template blank-typescript@sdk-57
cd MyMealApp
```

اقرئي [مرجع Expo 57](https://docs.expo.dev/versions/v57.0.0/) قبل نسخ أمثلة لإصدارات مختلفة. القالب ينشئ أساس مشروع، ولا يكتب منطق منتجك. تحققي من package.json بعد الإنشاء. ابدئي بشاشة بيضاء فيها اسم تجربة، ثم زيدي السعر والزر وحالة الاختيار. **دليل إتقان:** تغيير state يعيد الرسم، وتمرير props لا يغير الأب من داخل الابن مباشرة.

لا تبدئي بـLiquid Glass. عندما تعمل العناصر العادية أضيفي @expo/ui وglass-effect وفق وثائق النسخة و`npx expo install` الذي يختار الاعتمادات المتوافقة. تعلمي مكتبة واحدة بقدر ما تحتاجه الميزة.

## ٤. التصميم والمتطلبات قبل التوسع

اكتبي user stories بصوت المستخدم: «كمنظّم أريد تقليل الخانات مع معرفة ما خرج ولماذا». حددي شروط قبول قابلة للفحص، مثل «عند تقليل٩ إلى١ مع ركيزة متوافقة تبقى الركيزة وحدها». ارسمي في Figma البداية والتفضيلات والدعوة والاكتشاف والخطة والجيب والخطأ والانتظار. ضعي ERD وsequence ومواصفات endpoints قبل بناء الرحلة كاملة.

**دليل إتقان:** يستطيع زميل قراءة المخطط وتحديد من يستدعي API وأين تُحفظ البيانات، دون تخمين ما يفعله زر مبهم. تقسيم هذا الدليل إلى ملفات لا يغني عن Figma أو التبرير الذي تكتبينه بنفسك.

## ٥. مشروع ASP.NET Core فارغ

من مجلد مشروعك الجديد يمكن إنشاء backend رسمي بالـcontrollers:

```sh
dotnet new webapi --use-controllers -n MyMeal.Api -o backend/MyMeal.Api -f net10.0
dotnet run --project backend/MyMeal.Api --no-launch-profile --urls http://127.0.0.1:8000
```

هذه أوامر scaffolding. افتحي Program وافهمي AddControllers وMapControllers قبل إضافة endpoint خاص بك. لا تضعي قالب مثال WeatherForecast ضمن منتجك لمجرد أنه وُلد. **دليل إتقان:** GET بسيط يرجع JSON وأنك تعرفين method/path/status/body، وتستطيعين شرح أين يعالج الإطار الطلب.

بعد ذلك اكتبي Preferences صغيرة بنفسك وPOST يستقبلها ويرفض اسمًا فارغًا. اختبريه عبر عميل HTTP قبل ربط الشاشة. قارني فقط بعد المحاولة بفصلي النماذج والـAPI، وابحثي عن رسائل المترجم في الوثائق الأصلية.

## ٦. قاعدة البيانات للتسليم

لفهم حاتم الحالي يمكنك تجربة SQLite منفصلة. أما مشروع المدرسة فابدئي بقاعدة على خادم مثل PostgreSQL أو SQL Server، وصمّمي schema ومهاجرات بنفسك. لا تنقلي Store الحالي حرفيًا إلى driver آخر وتتوقعي تطابق اللهجة والأقفال والأنواع.

اقتراح بيانات للتفكير، **غير موجود حاليًا**: Users، Groups مع owner_user_id، GroupMembers، Experiences، MemberPreferences، علاقات للمطابخ والحساسيات، GroupExperienceState للجيب والمكتمل، Invitations، Sessions إذا اخترت جلسات. افصلي فقط ما يفيد علاقاتك واستعلاماتك؛ ليس عدد الجداول مقياس الجودة.

اكتبي أول INSERT وSELECT بمعاملات، ثم UPDATE وDELETE محددين بالهوية والمالك. اقرئي القيم بعد إعادة تشغيل الخدمة. **دليل إتقان:** البيانات لا تضيع، ولا يمكن لصف عضوية الإشارة إلى مجموعة غير موجودة، ولا تدمج قيمة مستخدم داخل SQL كنص تعليمات.

## ٧. الحسابات قبل اكتمال المنتج الأكاديمي

النسخة الحالية مفاتيح وصول بلا حسابات. لنسختك الأكاديمية صممي التسجيل والدخول والخروج من الواجهة إلى API إلى DB. افهمي الفرق: authentication يثبت من أنت، authorization يقرر ما يسمح لك فعله.

إذا اخترت كلمات مرور، استعملي مكتبة تجزئة مناسبة وإرشاداتها، ولا تعيدي اختراع التشفير ولا تستعملي SHA-256 الخام من مثال مفاتيح حاتم. اختاري جلسات أو JWT عن فهم، وحددي الانتهاء والخروج والإبطال. خدمة توصيل بريد إن استعملتِها لا ينبغي أن تستبدل منطق المصادقة المطلوب منك.

**دليل إتقان:** حساب جديد يسجل ثم يدخل ثم يخرج، والخروج له أثر حقيقي وفق تصميم الجلسة. عضو لا يستطيع تغيير مجموعة غيره حتى عبر طلب يدوي. إضافة شاشة login بلا حماية API ليست إنجاز المصادقة.

## ٨. أول رحلة من البداية للنهاية

ابني إنشاء مجموعة واحدًا: نموذج → client → POST → validation → transaction → DB → JSON → state → شاشة المجموعة. لا تبني عشر شاشات على بيانات وهمية وتؤجلي الاتصال إلى آخر أسبوع.

ضعي حالات الانتظار والفشل بجانب النجاح من البداية. لو فشل INSERT لا تغلقي النموذج برسالة نجاح. **دليل إتقان:** يمكن إغلاق التطبيق وفتحه واستعادة بيانات المجموعة بحسب نظام حسابك، ويمكن مشاهدة سجل الطلب وتشخيص فشله.

## ٩. انضمام العضو وصلاحياته

ولّدي رمز دعوة عشوائيًا، واعرضي صفحة join مستقلة. اكتبي قواعد ما يراه حامل الرابط وما يحتاج هوية عضو. اربطي العضو بالمجموعة من الخادم، ولا تثقي بمعرف مستخدم يرسله المتصفح دون التحقق من ملكيته.

**دليل إتقان:** نافذتا متصفح مستقلتان تمثلان منظّمًا وعضوًا، ولكل منهما الصلاحيات الصحيحة. العضو يعدل ذوقه، والمنظّم يشاهد أثره. الرد العام نفسه لا يحتوي قيود الآخرين، وليس مجرد إخفائها بواسطة CSS.

## ١٠. نقل قواعد الورقة إلى محرك مستقل

رتبي الإضافات: فحص ميزانية → خيار نباتي محدد → حساسية وتوثيق → نقاط لكل عضو → دمج النقاط → تقديم الركيزة → Take للسعة → جيب → مكتمل وتراجع. بعد كل إضافة اكتبي مثالًا ناجحًا وفاشلًا.

**دليل إتقان:** إذا نقص الوقت وحده فالخطة مقدمة الترتيب السابق. إذا مُنعت الركيزة تظهر المشكلة، وإذا زاد الوقت تعود التجارب المؤجلة تلقائيًا دون عودة المحفوظ يدويًا. إذا غيّرت الأذواق فمن الطبيعي أن يتغير الترتيب. اشرحي هذا الفرق في عرضك.

## ١١. واجهة كاملة ثم تحسين المظهر

اربطي الاكتشاف والخطة والجيب والمجموعة بنفس مصدر البيانات. أنشئي theme وT/Button/Sheet عند ظهور تكرار حقيقي. اجعلي النص العربي مقروءًا والمساحة الآمنة محفوظة والأزرار ذات أسماء وصول. أضيفي Glass للمناطق المناسبة وفحص التوفر والبديل. احتفظي بـdraft للنموذج وسعة الوقت؛ لا ترسلي طلبًا عند كل حركة إصبع دون حاجة.

**دليل إتقان:** شاشة هاتف ضيقة لا تتمدد أفقيًا، وفشل الشبكة يظهر مع إمكانية إعادة المحاولة، ولا يمحو polling تغييرًا أحدث. إذا احتجتِ لاحقًا مكتبة navigation، أضيفيها بسبب تدفق واضح مثل شاشات متداخلة وروابط عميقة، لا لمجرد اسمها المشهور.

## ١٢. التوثيق والاختبار والنشر

اكتبي OpenAPI وأمثلة status والمفاتيح. توليد أنواع TS اختياري مفيد لتقليل اختلاف العقد؛ افهمي أولًا النوع الذي يُولد. أضيفي اختبارات قواعد وتكامل ومتصفح باستخدام DB تدريب. انتقلي من localhost إلى استضافة ثابتة لخادمك وقاعدتك حين تحتاجين تسليمًا مستمرًا. Quick Tunnel ممتاز لإظهار تقدم مؤقت لأعضاء المجموعة، وليس دليل نشر دائم.

في Xcode اختبري نسخة Release على iPhone بعد ضبط عنوان API. **دليل إتقان:** يعمل النظام لزميل على جهاز مختلف، ويمكنه تشغيله من README والمخطط والمهاجرات دون خطوات سرية تعتمد على جهازك فقط.

## خطة جلسة تعلم واحدة

1. اكتبي سؤالًا واحدًا، مثل «كيف أرفض ميزانية دون٣٠؟».
2. اقرئي قسمًا من وثائق اللغة/الإطار، ثم أغلقي المثال.
3. اكتبي محاولة صغيرة بيدك وتوقعي الناتج قبل التشغيل.
4. اقرئي أول خطأ، وحددي الملف والسطر والقيمة والنوع.
5. اكتبي اختبارًا يثبت الحالة الصحيحة والخاطئة.
6. سجّلي ما فهمته وما لم تفهميه، والمصدر الذي قرأته والتغيير الذي نفذته فعلًا.
7. أنشئي commit يصف تغييرًا مكتملًا صغيرًا. لا تنشئي سجلًا مصطنعًا يوحي بتاريخ عمل غير حقيقي.

Git محليًا: `git status` لمعرفة التغييرات، `git diff` لقراءتها، `git add <file>` لاختيارها، `git commit` لتسجيلها، و`git push` لرفعها إلى الريموت المضبوط. الفرع نسخة عمل داخل نفس المستودع، وليس مستودعًا جديدًا. `codex/dotnet-backend` فرع النسخة المشروحة؛ في مشروعك اختاري أسماء تعكس عملك.

## أسئلة تثبت أنك فهمتِ

لماذا الاسم ليس مفتاحًا أساسيًا؟ لماذا لا نعيد المتوسط قبل فحص الميزانية؟ أين تنفّذ validation؟ لماذا يستخدم العميل spread لكل Settings؟ ما الفرق بين الدعوة ومفتاح المنظّم؟ ماذا يحدث لبيانات state بعد إعادة تشغيل التطبيق؟ لماذا نحتاج transaction عند الانضمام؟ هل TypeScript تتحقق من JSON وحدها؟ ماذا ينكسر إذا أغلقنا النفق؟ ولماذا لا تكفي صفحة login وحدها؟

إذا استطعتِ الإجابة مع الإشارة للسطر والاختبار، ثم كتابة نسخة أصغر دون فتح الحل، فأنت تبنين فهمًا يمكن الاعتماد عليه. هدفك النهائي ليس حفظ حاتم حرفيًا؛ كتابة نظام تؤلفين قراراته وتشرحينها وتختبرينها بنفسك.
