## لماذا نعرّف نماذج قبل الشاشات؟

تحتاج الواجهة والخادم اتفاقًا على معنى «تفضيلات». هل الميزانية رقم؟ هل يمكن حذف الاسم؟ هل الركيزة تجربة واحدة أم قائمة؟ النماذج تجيب عن شكل البيانات، والتحقق يجيب عن صلاحيتها، والمخطّط يجيب عما نفعل بها. `DTO` اختصار لكائن ينقل البيانات بين أجزاء النظام؛ ليس جدولًا بالضرورة.

## Models.cs: الأسطر ١–٤٦، القوائم المحددة

أسطر `using` تستورد أدوات وصف القيم الافتراضية، والتحقق، وتحويل JSON. `namespace Hatim.Api` يجمع الأنواع. كل `enum` مجموعة خيارات محددة:

| النوع | الأعضاء ومعناهم |
|---|---|
| `Role` | `Resident` مقيم و`Visitor` زائر؛ سياق الذوق، وليس صلاحية أمنية |
| `Cuisine` | سعودي، ياباني، إيطالي، شامي، آسيوي، قهوة وحلى |
| `Allergen` | مكسرات، فول سوداني، حليب، قمح، سمسم، قشريات، سمك، بيض، صويا |
| `Category` | مطابخ جديدة، كنوز مخفية، افتتاحات، طبق ولحظة |
| `Priority` | ركيزة، أساسية، مرنة |

```csharp
[JsonStringEnumMemberName("مقيم")] Resident
```

داخل C# الاسم `Resident`، وفي JSON القيمة `"مقيم"`. السمة بين `[]` تصف الاسم الخارجي. بهذه الطريقة لا تحتاج الواجهة تخمين معنى رقم مثل `0`. تعريف enum وحده لا يمنع استقبال أرقام JSON؛ إعداد المحوّل في نهاية الملف يمنعها.

## الأسطر ٤٨–٥٩: Preferences

```csharp
public sealed record Preferences
{
    private string name = null!;
    [Required, StringLength(30, MinimumLength = 1)]
    public required string Name { get => name; init => name = value?.Trim()!; }
    // بقية الخصائص موجودة في الملف الأصلي
}
```

السطر الأول يعرّف نوع بيانات متاحًا لبقية المشروع وغير قابل للوراثة. `name` حقل داخلي يخزن الاسم. `Name` واجهة القراءة والإسناد لهذا الحقل. عند الإنشاء يستقبل `init` قيمة في المتغير الضمني `value`، و`Trim` يزيل فراغات الأطراف. لذلك `"  أمل  "` تصبح `"أمل"`، والاسم المكوّن من فراغات يفشل التحقق. `null!` لا يحوّل null إلى نص؛ يسكّت تحذير المترجم، بينما طبقة استقبال JSON والتحقق مسؤولة عن رفض البيانات غير الصالحة.

`Required` يطلب قيمة غير فارغة، و`StringLength` يضع الحد ١–٣٠. `required` في تعريف الخاصية عقد إضافي مع مُنشئ الكائن/قارئ JSON، وليست هذه الكلمات الثلاث مترادفات.

| الخاصية | الافتراضي | معناها والتحقق |
|---|---|---|
| `Name` | يجب توفيرها | اسم العرض، تقليم فراغات وحد طول |
| `Role` | `Resident` | مقيم أو زائر |
| `Cuisines` | `[]` | قائمة أذواق، بطول أقصى ٦ |
| `Allergies` | `[]` | قائمة حساسية، بطول أقصى ٩ |
| `Vegetarian` | `false` | هل يلزم خيار نباتي؟ |
| `Mild` | `false` | تفضيل غير الحار |
| `Budget` | `200` | عدد صحيح بين ٣٠ و٥٠٠، للشخص لكل تجربة |

الإسناد `= 200` هو الذي يحدد الافتراضي وقت الإنشاء. `[DefaultValue(200)]` تصفه للأدوات والتوثيق. `MaxLength` يحدد طول القائمة؛ لا يضمن عدم تكرار عناصرها. المخطّط يستعمل `Distinct()` للحساسيات و`Contains` للمطابخ، فلا يكسب الشخص نقاطًا مضاعفة بتكرار مطبخ.

## الأسطر ٦١–٨٤: Member وExperience

`Member(string Id, Preferences Preferences, bool Organizer = false)` صيغة record مختصرة تنشئ الخصائص والباني. المعرف هو الهوية الثابتة، والاسم قابل للتغيير. `Organizer` هو الذي يميز المنظّم في هذه النسخة. الخادم يحدده عند الإنشاء، ولا يقبل من العميل ترقية نفسه بإرسال هذا الحقل داخل Preferences.

`Experience` وصف تجربة واحدة. راقبي الفرق بين `Id` الداخلي، و`Title` اسم التجربة، و`Venue` المكان الذي يقدمها:

| الخصائص | كيف تُستخدم؟ |
|---|---|
| `Id`, `Title`, `Venue`, `Neighborhood` | ربط الخطة بالكتالوج وعرض التفاصيل والبحث |
| `Category`, `Cuisine` | فلترة الواجهة وحساب التوافق |
| `Description`, `Why` | وصف التجربة وسبب الاختيار التحريري |
| `Image` | مفتاح مثل `fire`، يربطه `theme.ts` بصورة محلية |
| `Price`, `Minutes` | السعر شرط، والدقائق معلومات عرض؛ لا يوجد جدولة زمنية بالدقائق |
| `Editorial` | نقاط ترتيب تحريرية؛ ليست تقييم مستخدمين أو نسبة احتمال |
| `Vegetarian`, `VegetarianOption` | نباتية أصلًا أو تعديل محدد يناسب النباتي |
| `Spicy`, `MildOption` | هل هي حارة؟ وهل يوجد تعديل للحرارة؟ |
| `Allergens` | مكونات الحساسية المذكورة |
| `VerifiedFreeOf` | ما ثُبت غيابه مع التعامل مع التلامس العرضي |

وجود `string?` يعني أن الخيار قد يكون null. القوائم الافتراضية فارغة. **غياب مكوّن من قائمة Allergens لا يثبت أن التجربة آمنة له**؛ لذلك توجد قائمة توثيق منفصلة. في البيانات الحالية كل `verified_free_of` فارغة، والبيانات كلها توضيحية؛ إدخال حساسية قد يمنع الكتالوج كاملًا كما تقضي القاعدة.

## الأسطر ٨٦–١١١: Settings

هذا النوع يمثل اختيارات المجموعة التي نحفظها، وليس الخطة الناتجة:

```json
{
  "slots": 9,
  "anchor_id": "fire",
  "pocket_ids": [],
  "completed_ids": []
}
```

`Slots` إجمالي الخانات بما فيها المستهلكة. `AnchorId` معرف الركيزة أو null لتحريرها. `PocketIds` فقط الحفظ اليدوي. `CompletedIds` ما عاشت المجموعة تجربته. الجيب التلقائي المحسوب لا يُكتب في `PocketIds`، وإلا لما رجعت التجارب تلقائيًا حين يزيد الوقت.

الحقول الداخلية تمنحنا فرصة تقليم معرفات الإدخال. `Select(id => id?.Trim()!)` يمر على العناصر، ثم `ToArray()` يبني مصفوفة جديدة. توضع حدود الطول والعدد، ثم `IValidatableObject` يضيف قواعد تجمع أكثر من خاصية.

`Validate(...)` يعيد تسلسل أخطاء. كل `yield return new(...)` يضيف خطأ ولا يمنع فحص الشروط التالية:

1. عدد العناصر بعد `Distinct()` يجب أن يساوي العدد قبلها؛ وإلا توجد تجربة مكتملة مكررة.
2. نفس الفحص للحفظ اليدوي.
3. لا يجوز أن يصبح `Slots` أقل من عدد المكتمل، لأن الخانات المستهلكة لا تختفي.
4. الركيزة لا تكون محفوظة يدويًا في الجيب في الوقت نفسه.
5. `Intersect` يجد التقاطع بين الجيب والمكتمل؛ يجب أن يكون فارغًا.
6. `Any(string.IsNullOrWhiteSpace)` يرفض معرفًا فارغًا أو فراغات أو null ضمن القوائم.

هذا تحقق في البنية والعلاقات. أما «هل المعرف موجود في الكتالوج؟» فيفحصه controller لأنه يملك Catalog. و`Planner.Build` يفترض وصول Settings صالحة؛ استدعاؤه يدويًا في برنامج آخر لا ينفذ DataAnnotations تلقائيًا.

## الأسطر ١٢٨–١٤٩: ApiJson

`Options` إعداد موحّد للـJSON. `Create` تنشئ إعدادًا وتستدعي `Configure` ثم تعيده. نستعمل `Configure` أيضًا لضبط serializer الخاص بـASP.NET Core، حتى تتفق API مع النصوص المخزنة في DB.

`SnakeCaseLower` تحول `InviteCode` إلى `invite_code`. `PropertyNameCaseInsensitive = false` تجعل الاسم الخارجي حساسًا لحالة الحروف. `UnmappedMemberHandling.Disallow` ترفض حقولًا مجهولة مثل `admin` داخل Settings. `NumberHandling.Strict` لا تقبل نص `"200"` بدل الرقم `200`. `RespectNullableAnnotations` تحترم nullability للخصائص المدعومة؛ ليست فحصًا شاملًا لكل عنصر داخل كل generic، لذلك توجد قواعد واختبارات إضافية. `JsonStringEnumConverter` يستعمل أسماء enums النصية ويرفض قيمها العددية.

`Text<T>` يحول كائنًا إلى نص JSON. `Read<T>` يعيد كائنًا من نص، ويرمي `JsonException` إن كانت النتيجة null. الحرف T مكان لأي نوع نمرره، مثل `Read<Settings>`.

## Planner.cs: Evaluate، الأسطر ١–٥٠

`Planner` نوع static لأن الحساب لا يحتاج ذاكرة مشتركة. `Evaluation` يحمل ثلاث نتائج: أسباب المنع، تعديلات ممكنة، نقاط. نقول إن الحساب «نقي» هنا لأنه لا يغير قاعدة بيانات ولا يرسل شبكة ولا يغير مدخلاته؛ يمكن تجربته مباشرة داخل اختبار.

الأسطر ١٠–١١ تنشئ ثلاث قوائم فارغة. داخل `foreach` يأخذ `p = member.Preferences` اختصارًا. لكل حساسية مختلفة: يحول enum إلى الاسم العربي باستعمال نفس JSON serializer، ثم يفحص وجودها المعلن أولًا. إن وجدت، يسجل تعارضًا حتى لو زعمت بيانات متناقضة أنها موثقة الغياب. وإلا يفحص `VerifiedFreeOf`؛ عدم وجود توثيق يضيف سبب منع أيضًا.

الأسطر ٢٣–٢٨ تفحص النباتية: إذا كان الشخص نباتيًا والتجربة ليست كذلك، نبحث عن `VegetarianOption` غير فارغ. عند وجوده نكتبه ضمن التعديلات باسم الشخص. عند غيابه نسجل منعًا. «نبحث عن مخرج» هنا لا يعني تخمين وجبة بديلة من عندنا.

الأسطر ٢٩–٣٠ تقارن السعر بميزانية **كل شخص**. شخص بميزانية ٨٠ لا يُتجاهل لأن متوسط المجموعة ٢٠٠. سعر ٩٠ يفشل له حتى لو أحب الجميع المطبخ.

الأسطر ٣١–٤٤ تحسب affinity لكل عضو:

| الحالة | الأثر |
|---|---|
| المطبخ ضمن أذواقه | +٢٠ |
| يفضّل غير الحار والتجربة حارة مع تعديل | شرح التعديل، دون خصم |
| يفضّل غير الحار، والتجربة حارة ولا تعديل | −٢٠ وتنبيه، دون منع بسبب هذا التفضيل وحده |
| زائر وتجربة سعودية | +٥ |
| مقيم وتجربة كنز مخفي | +٥ |

بعد كل عضو تضاف affinity إلى القائمة. ثم تبدأ النقاط من `Editorial`. إذا كانت هناك أعضاء، نضيف ٧٠٪ من متوسط affinity و٣٠٪ من أقل affinity. الجزء الثاني يمنح أثرًا للشخص الأقل توافقًا، لكنه ليس إثباتًا رياضيًا للعدالة ولا يتغلب على قيد صلب. وأخيرًا نحول القوائم إلى مصفوفات ونقرّب الرقم لمنزلتين بطريقة `ToEven`.

### مثال من البيانات الحالية

أمل زائرة تحب السعودي، وبدر مقيم يحب الياباني. الميزانيات ٢٠٠، ولا قيود إضافية. تجربة `fire` نقاطها التحريرية ٩٦. أمل تحصل على ٢٥ وبدر صفر:

```text
المتوسط = (25 + 0) / 2 = 12.5
الأقل = 0
النتيجة = 96 + 0.7 × 12.5 + 0.3 × 0 = 104.75
```

`sushi` تبدأ من ٩١؛ أمل صفر وبدر ٢٠، فتصبح ٩٨. درجة تتجاوز ١٠٠ عادية هنا؛ ليست نسبة مئوية. وإذا أضفنا قيدًا يمنع fire، لا تنقذها ١٠٤٫٧٥ نقطة.

## Build: الأسطر ٥٢–٩٨

تبدأ بقائمة مرشحين، وجيب، و`anchorIssue = null`. ثم تمر على الكتالوج بالترتيب:

| الأسطر | ماذا يحدث ولماذا؟ |
|---|---|
| ٥٩ | التجربة المكتملة تُتخطى؛ موجودة في سجل المكتمل أصلًا |
| ٦٠–٦٤ | المحفوظة يدويًا تذهب للجيب بسبب الحفظ ثم `continue`؛ لا نعيد إدخالها تلقائيًا |
| ٦٥–٧٣ | تقييم التجربة؛ إن وجدت أسباب منع، نجمعها بنص ونضعها في الجيب بـ`Blocked=true`، ونكتب مشكلة خاصة إن كانت الركيزة |
| ٧٤–٨١ | نحدد هل هي ركيزة، ونجد أسماء من يحبون مطبخها؛ الركيزة لها سبب خاص، والبقية لها السبب التحريري مع أسماء المتوافقين |
| ٨٢–٨٣ | إنشاء Decision مرشح يحمل النقاط والتعديلات |
| ٨٥–٨٨ | ترتيب المرشحين ثم إسناد أساسية/مرنة |
| ٨٩–٩٢ | حساب المتاح وحجز خانة الركيزة الممنوعة واختيار ما يسع |
| ٩٣–٩٤ | نقل فائض الوقت إلى الجيب بسبب مستقل |
| ٩٥–٩٦ | إعادة Plan متكاملة |

لاحظي ترتيب الحفظ اليدوي قبل التقييم: تجربة محفوظة يدويًا تحمل سبب الحفظ في الجيب، ولا يعني `Blocked=false` لها في هذا المسار أنها فُحصت وثبت توافقها. عندما تُعاد للترتيب، تمر بفحص القيود مجددًا.

### تفكيك سلسلة الترتيب

```csharp
var ranked = candidates.OrderBy(d => d.ExperienceId != settings.AnchorId)
    .ThenByDescending(d => d.Score).ThenBy(d => d.ExperienceId, StringComparer.Ordinal)
    .Select((d, index) => d.Priority == Priority.Anchor ? d
        : d with { Priority = index < 3 ? Priority.Core : Priority.Flexible }).ToArray();
```

`OrderBy` يرتب false قبل true. الركيزة تعطي false في اختبار «هل المعرف مختلف؟»، فتأتي أولًا. `ThenByDescending` يرتب بقية العناصر من أعلى نقاط إلى أدناها. تعادل النقاط يحسمه المعرف بـ`Ordinal` حتى يبقى القرار ثابتًا. `Select` يعيد الركيزة كما هي، ويسمي غيرها أساسية عندما يكون فهرسها أقل من ٣، ومرنة بعد ذلك. الفهرس يبدأ من صفر: مع وجود ركيزة تكون التالية اثنتين أساسيتين، وليس ثلاثًا إضافية.

### لماذا تنكمش الخطة دون أن تختلط؟

عدد الخانات لا يدخل معادلة النقاط أو الترتيب. يدخل **بعد الترتيب** في `Take(capacity)`، ومعناه خذي أول N عناصر. `Skip(capacity)` يعيد الباقي. إذا كانت القائمة `A,B,C,D`، فإن أربع خانات تختارها كلها وخانتين تختاران `A,B`. هذا الضمان يفترض ثبات الأعضاء والكتالوج والركيزة والحفظ والمكتمل؛ تغيير الذوق قد يغير الترتيب بحق.

```csharp
var remaining = settings.Slots - settings.CompletedIds.Length;
var capacity = Math.Max(0, remaining - (anchorIssue is not null && remaining > 0 ? 1 : 0));
```

الأول يطرح المستهلك. الثاني يحجز خانة إن كانت الركيزة ممنوعة وهناك وقت متبقٍ. `Math.Max(0, ...)` يمنع سعة سالبة. عشاء واحد مع ركيزة ممنوعة يعني **صفر تجارب مختارة وخانة غير معبأة**، حتى يتخذ المنظّم قرارًا صريحًا. لا نختار تجربة ثانية ونسمّيها حلمه.

`Available` هو عدد الخانات بعد خصم المكتمل، و`Unfilled = remaining - selected.Length`. قد تكون أكثر من خانة إذا لم توجد تجارب متوافقة. لا نملأ الأرقام على حساب القيود.

## Catalog: الأسطر ١٠٠–١٠٩ وملف JSON

## تمارين دون نسخ الحل

1. ارسمِي ثلاث تجارب وعضوين على ورقة، وطبقي القيود قبل النقاط.
2. اكتبي دالة مستقلة تحسب affinity لشخص واحد فقط، واختبريها بأربع حالات.
3. اجعلي الركيزة ممنوعة وخانتين متاحتين. المتوقع حجز خانة، وقد تختار الخوارزمية تجربة واحدة فقط.
4. احفظي تجربة يدويًا، ثم وسّعي الوقت. يجب ألا ترجع قبل إلغاء الحفظ اليدوي.
5. بعد تجربتين مكتملتين، جرّبي `Slots=1`. ينبغي أن يفشل التحقق قبل الترتيب.
