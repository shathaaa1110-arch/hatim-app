# خطة التنفيذ والتسليم والتحقق

وثيقة تخص الكود الحالي، وتكمل [مراجعة المتطلبات](school-readiness.ar.md). لا تسند عملًا إلى أعضاء غير معروفين ولا تختلق تواريخ إنجاز شخصية.

## قصص المستخدم ومعايير القبول

| الأولوية | القصة | معيار القبول |
|---|---|---|
| أساسية | كمقيم أو زائر أريد اكتشاف تجارب قبل الالتزام | أفتح التطبيق فأرى الاكتشاف، وأبحث وأقرأ التفاصيل دون تسجيل أو إنشاء قروب. |
| أساسية | أريد خطة تتكيف مع الوقت | أحدد1–9 خانات، وأرى الركيزة والأولوية والسبب؛ التقليص يحفظ المستبعد في الجيب ويحترم الوجبات المكتملة. |
| أساسية | أريد مراعاة قيود الرفقة | يدخل المدعو تفضيلاته، وتُعاد الخطة مع رفض التجارب غير الآمنة، ولا تظهر تفاصيل قيوده لبقية المدعوين. |
| أساسية | أريد حسابًا أعود منه إلى خططي | أسجل أو أدخل من حسابي، أنشئ خطة، أخرج، ثم أدخل من متصفح نظيف فأجدها. الجلسة الملغاة لا تديرها. |
| أساسية | أريد إدارة خططي | أغيّر اسم خطة، ألغي طلب الحذف فلا تتغير، ثم أؤكده فتختفي ويتوقف رابطها؛ تبقى خططي الأخرى. |
| أساسية | أريد حفظ خطتي القديمة | الربط صريح ويحتاج مفتاحها؛ يظل الذوق والجيب والركيزة والدعوة دون تغيير، ويُلغى مفتاح الإدارة القديم. |
| أساسية | أريد أخطاء مفهومة | عند انقطاع API تظهر إعادة المحاولة، ولا تُمسح الجلسة بسبب503 ولا ينجح الحفظ شكليًا. |
| إضافية | أريد قروبًا ثابتًا وتصويتًا | أدخل قروباتي اختياريًا، أحفظ أعضاءه، وأرى التصويت والقرعة والقيادة والطرد وفق صلاحيات API. |

## ترتيب البناء اليدوي

1. ارسمي رحلة الاكتشاف والخطة والحساب والدعوة في Figma، وحددي عناصر كل شاشة ورسائلها.
2. اكتبي ERD ثم migrations في PostgreSQL. ابدئي بالحسابات والجلسات والخطة والرفقة؛ القروبات الدائمة تأتي بعد الأساس.
3. أنجزي API صغيرًا بالتسجيل والدخول والخروج ثم CRUD خطة، واختبريه من Swagger.
4. ابني الواجهة، ثم اربطي كل حدث بطلبه. أضيفي حالات التحميل والرفض قبل تحسين الشكل.
5. اختبري القرار والقيود واسترجاع الحساب على جهازين، ثم أضيفي القروبات إذا بقيت ضمن النطاق.
6. انشري نسخة اختبار بعنوان ثابت بعد اختيار الاستضافة، واختبريها من كل جهاز، ثم جهزي التسليم.

## خطة Git وSCM

العمل الحالي على `codex/persistent-groups` في المستودع الخاص. `codex/python-postgres` يحفظ النسخة الأصلية و`codex/dotnet-backend` يحفظ البديل السابق. ابدئي كل تغيير في فرع واضح، وراجعي الفرق قبل الدمج. لا تعدلي ترحيلًا مطبقًا؛ أضيفي ملفًا مرقمًا. حدّثي OpenAPI والشرح مع التغيير. احتفظي بأسرار DB والجلسات خارج Git. ملفات القفل تدخل المستودع لتكرار التثبيت.

للفريق: اجعلي لكل مهمة معيار قبول ومالكًا يختاره الفريق وتاريخًا واقعيًا في لوحة إدارة المشروع. لا يعني هذا المستند أن اللوحة أُنشئت أو أن الأعضاء نفذوا القصص. مراجعة Pull Request تربط المشكلة بالتغيير ونتيجة الاختبار، ولا تنسب العمل لغير صاحبه.

## خطة QA

| الطبقة | الاختبار | دليل الفشل الذي نبحث عنه |
|---|---|---|
| محرك القرار | pytest وبيانات المقارنة | ركيزة تُستبدل بصمت، تجاهل حساسية، فقد جيب أو خانة مكتملة |
| API + PostgreSQL | مخطط مستقل لكل اختبار | وصول حساب آخر، جلسة منتهية مقبولة، كتابة جزئية، طلبان متزامنان متعارضان |
| الواجهة الكاملة | Playwright وحسابات وهمية | زر لا يستدعي الخادم، حفظ شكلي، فقد بيانات بعد reload، أخطاء شاشة/شبكة |
| iOS | Release في المحاكي | تنقل أو Sheet مكسور، واجهة ضيقة، مشكلة اتصال localhost |
| حاوية النشر | Docker + PostgreSQL اختبار | migrations تفشل، ملفات الويب غائبة، عدم صلاحية المستخدم غير root |
| قبول الفريق | أجهزة حقيقية بعد النشر | إعداد ناقص على جهاز زميل، عنوان مؤقت منتهي أو صلاحيات غير صحيحة |

شغّلي `npm run check` و`npm run format:check` وRuff. للمتصفح: `npm run web:build` ثم `npm run test:e2e:server` في طرفية، و`HATIM_TEST_URL=http://127.0.0.1:8002 npm run test:e2e` في أخرى. خادم الاختبار ينشئ schema عشوائية ويحذفها عند الإيقاف الطبيعي. لا تختبري الحذف على بياناتك الشخصية.

التعامل مع خطأ: سجلي خطوات الإعادة والنتيجة المتوقعة والفعلية، أصلحي السبب، ثم أعيدي الاختبار المتأثر والاختبارات ذات الصلة. لا توسعي الاختبارات بلا سبب بعد النجاح. التشغيل الحقيقي على iPhone والنشر الدائم يظلان قبولًا مستقلًا عن متصفح الاختبار.
